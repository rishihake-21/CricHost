## Current slice details

The current API includes platform foundation, local identity/session flows, allowlisted platform-admin TOTP step-up, audit/outbox persistence and Redis publication, tenant provisioning and membership administration, tournament configuration, independent player profiles and tournament applications, team/roster management, deterministic round-robin fixtures and standings, auction setup through transactional settlement and worker progression, public auction snapshots/SSE, match/scoring/adjudication with transactional standings, public match snapshots/SSE, tenant-scoped asset upload/moderation, sponsor profiles/campaigns/public placements, tenant usage snapshots and quota checks for selected resource creation paths. MFA-protected platform routes support plan provisioning, tenant subscription inspection/assignment and audited dead-letter listing/replay. External alert delivery is not configured. Invitation acceptance works with verified accounts; production email delivery remains an integration gate. Production quota-checked operations still fail until each tenant is configured with a plan, while development tenants may remain unconfigured. Asset storage currently uses a private local filesystem adapter and scanning requires configured ClamAV. The API uses Mongoose as the implementation adapter because the supplied LLD and scaffold already choose it; this is not a claim that the source documents closed ADR-001. Re-evaluate the database decision and production storage/operations before launch.

Identity stores only token hashes. Access tokens expire quickly; refresh tokens rotate atomically against the prior hash. Cookies are HttpOnly and SameSite=Lax, Secure in production. Passwords use bcrypt. Local development can expose a one-time email verification token only when `IDENTITY_EXPOSE_DEV_TOKENS=true`; production registration fails closed until a real email delivery provider is configured. Do not enable development tokens in production.

No tests or runtime verification were run. The auction worker now opens queued lots and finalizes expired lots automatically when its process is running and MongoDB transactions remain healthy. The product remains incomplete and is not production-ready.
