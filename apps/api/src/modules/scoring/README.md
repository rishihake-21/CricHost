# Scoring

The initial scoring slice records one normalized delivery per append-only event. Each command must carry a UUID `clientEventId`, expected innings event sequence and active scorer `leaseEpoch`. A duplicate ID with the same normalized payload returns the existing event; reuse with a different payload is rejected. Sequence checks serialize concurrent submissions, and a stale lease epoch is rejected rather than merged.

Delivery and correction events are append-only at the Mongoose model boundary; score projection updates and tenant-private outbox notices commit with them in one MongoDB transaction. The event log records striker, bowler, delivery type, bat/extras runs, completed runs and dismissal. Owner/admin corrections target an original delivery, include an audit reason, and append a revised interpretation; the server replays every delivery and latest correction in event order to rebuild runs, wickets, legal balls and wides/no-balls/byes/leg-byes. Wides and no-balls do not advance legal-ball count. While the match remains live, corrections can reopen an automatically completed innings when the revised projection no longer meets its close condition. A manual innings closure remains in force. Limited-over innings close automatically at the configured wicket or legal-ball limit; Test innings have no over-based automatic close. Delivery append requests are process-locally limited to 300 per minute per IP, lease requests to 30 per minute per IP and corrections to 30 per minute per IP; use a shared store for multiple API replicas.

Current limits: strike rotation and batter/bowler card projections are not derived yet; the initial delivery command records striker dismissals only and no-ball/wide laws are only partially constrained. Post-completion score correction and standings recomputation, declarations/follow-on enforcement, complete Test/custom rules, public player-by-player scorecards, scorer offline conflict UI, and cricket-domain review remain future work. Public snapshots expose team and innings totals only. Test/custom match outcomes require explicit owner/admin adjudication. A tied standard limited-overs score under SUPER_OVER or REPLAY policy requires an audited owner/admin resolution; super-over/replay innings are not modeled. Transactions require a replica set or sharded MongoDB deployment.
