# Platform administrator security

Platform administrator IDs are bootstrapped out of band through `PLATFORM_ADMIN_USER_IDS`, a comma-separated list of verified user IDs. The API does not provide a route for granting or removing the platform role. Configure `PLATFORM_MFA_ENCRYPTION_KEY` as 32 random bytes encoded in 64 hexadecimal characters and store it in a secret manager. Changing this key makes existing encrypted TOTP secrets unreadable and requires an out-of-band recovery.

An allowlisted administrator confirms their password to start enrollment, registers the returned `otpauth://` URI with an authenticator app, then confirms with a six-digit TOTP code. Ten single-use recovery codes are returned once; only their hashes are stored. TOTP secrets are encrypted with AES-256-GCM. Step-up verification is bound to the current login session for five minutes; session refresh clears the elevated state, and each TOTP time step can be accepted only once. An administrator with an active second factor can replace the authenticator after a fresh step-up and password confirmation. Confirming replacement rotates recovery codes, revokes other sessions, and clears step-up on the current session.

All platform plan management, tenant subscription inspection/assignment, and dead-letter listing/replay routes pass through `requirePlatformAdminStepUp`. Sensitive responses use `Cache-Control: private, no-store`. Enrollment and verification currently use process-local rate limits; a shared limiter is required before horizontal production scaling. Account recovery, MFA recovery when all factors are lost, tenant-administrator MFA, and a production bootstrap workflow for the first verified administrator remain open. See the [platform administrator runbook](../../../../../docs/runbooks/platform-admin.md) before configuring an administrator.
